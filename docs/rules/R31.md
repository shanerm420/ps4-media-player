# R31

**Two threads write the playback flags with no lock** - `s_playing`, `s_quit` and `s_track_finished` are declared `volatile int` in `src/main.c:157-159`; the SDL loop sets them, and `audio_thread` also writes them at the end of a track (`s_playing = 0; s_track_finished = 1;`, `src/main.c:1883-1885`), while `src/main.c` holds no `pthread_mutex` anywhere, so `volatile` is being asked to do a synchronization primitive's job

**Status:** found in source (read 2026-11-24), not fixed  
**Evidence:** `volatile` orders nothing in C11: it does not make a read-modify-write atomic, and it does not stop the compiler from moving the flag across the buffer it guards, so a stale or reordered read can start a track the loop has already stopped, or leave the thread playing one the loop believes is over. Fix it in its own round, with one owner per flag: the loop asks for the change and the audio thread performs it under a `pthread_mutex_t`, or the thread is handed a generation number when a track starts and stops when the generation moves. The pattern is already in this codebase - `src/applog.c` holds `s_mtx` across every write. `make check` cannot see this race (the host tests pass either way), so the fix is proven by a console run that stalls and repeats a track, read from the audio summary in the log
